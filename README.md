# pi-opsx-dev-reviewer

A portable kit that turns **pi** (pi.dev) into a delegating, self-guarding software
factory: a **design → implement → review → document** pipeline where a read-only main
agent delegates to specialist subagents, structural guards fail closed, review evidence
is produced by a neutral party, and every change **ratchets into durable back-pressure**
so the harness learns over time (scoped learnings, a per-skill trust ledger, and standing
goals re-verified forever).

Install globally with `./install.sh`, or drop the whole harness into a repo with
`./install.sh --here [repo]`.

**Full visual reference:** open [`index.html`](index.html) for a single-page guide to every
protection, agent, extension, and recipe, with usage — self-contained, opens straight from disk.

## How it works

- **Subagents = process isolation.** pi has no built-in roles; the community
  extension [`@mjakl/pi-subagent`](https://github.com/mjakl/pi-subagent) adds a
  `subagent` tool that spawns a **separate `pi` process** per call, with its own
  model, its own system prompt, and its own tool allowlist. Six markdown files in
  `~/.pi/agent/agents/` define the six roles.
- **Read-only is real, not prompted.** `reviewer.md` sets `tools: read,find,ls,grep`
  — dropping `edit`/`write`/`bash` means the reviewer roles *physically cannot* change files.
- **Independent judgment = different model family.** The reviewer's value is *not*
  sharing the developer's blind spots — keep them cross-family (for example, developer on
  `openai-codex/gpt-5.6-sol`, reviewer on `anthropic/claude-sonnet-5`). The shipped default
  is all-OpenAI for reachability (developer on the `gpt-5.6-sol` frontier tier, reviewer on
  the `gpt-5.6-terra` balanced tier — a different model, same family); see the cross-family
  caveat below.
- **Forcing apply is a pi-layer trick, not an OpenSpec feature.** OpenSpec's apply
  is single-agent by default and has no native delegation. The `force-delegate`
  extension blocks the main agent's `write`/`edit`/`bash` tool calls, so the only
  way it can change code is to call `subagent → developer`. The extension no-ops inside
  a delegated child whose trimmed `PI_SUBAGENT_DEPTH` is a positive safe integer, so the
  developer keeps full tools and does the actual work.

## Install (global, per machine)

```bash
./install.sh
```

It: verifies `pi`, installs `@mjakl/pi-subagent` (warning + stopping if another
subagent extension would collide), copies the agent files into
`${PI_CODING_AGENT_DIR:-~/.pi/agent}/agents/`, and installs the global worktree canary
directly at
`${PI_CODING_AGENT_DIR:-~/.pi/agent}/extensions/worktree-canary/index.ts`. Run this
global setup once per machine before using a worktree.

**Roles map onto the change lifecycle:** `solution-architect` settles the design
(contracts, enums, boundaries) and records the rationale in `design.md`/`specs/`
→ `spec-reviewer` red-teams the spec → `developer` implements code/tests against those
settled contracts → `reviewer` adversarially verifies → `tech-writer` documents the
user-facing delta → `architecture-writer` refreshes the repo-scoped `docs/architecture/`
arc42 tree when the change affects architecture. The architect edits design artifacts
ONLY (never production code); if design reveals code must change, it flags that in its
handoff.

**Models:** the agent files pin `gpt-5.6-sol` on the `openai-codex` provider
(solution-architect, developer, and architecture-writer — the heavy reasoning/synthesis
roles, on the frontier tier) and `gpt-5.6-terra` (reviewer, tech-writer, spec-reviewer, and
evolution-narrator — the balanced tier). This is an all-OpenAI configuration for a machine
where `openai-codex` (ChatGPT Plus/Pro `/login`, officially endorsed by OpenAI) is the
available provider, so every agent resolves out of the box. List what your machine can reach
with `pi --list-models`, then edit the `model:` line in any agent file to repoint — see the
cross-family caveat below.

**Cross-family caveat:** the reviewer's value comes from *not* sharing the developer's
blind spots (see [`docs/decisions/0001-cross-family-reviewer.md`](docs/decisions/0001-cross-family-reviewer.md)).
An all-OpenAI setup gives the reviewer a different *model* (`gpt-5.6-terra` vs the developer's
`gpt-5.6-sol`) but the same family, so correlated blind spots survive — fine for smoke-testing
the mechanism, weaker for real review. To restore true cross-family coverage, point the
reviewer at a non-OpenAI provider you have configured, for example `anthropic/claude-sonnet-5`.
(Anthropic via a Claude Pro/Max OAuth login bills as per-token "extra usage," not against
your plan — pi warns via `warnings.anthropicExtraUsage`; use Bedrock to stay on plan/credits.)

## Use it — ad hoc (no OpenSpec)

In any pi session or headless:

```bash
pi -p "Implement <X> with the developer agent, then have the reviewer agent
        check the diff and give me its verdict."
```

## Use it — force `/opsx:apply` (per OpenSpec project)

1. **Hint** (best-effort): append the block in `openspec/apply-policy.config.yaml`
   to the end of your repo's `openspec/config.yaml` `context: |` block. This tells
   the agent *how* to delegate. (Note: in the default `spec-driven` schema, `context`
   is injected at artifact creation and `rules` are per-artifact — neither is
   guaranteed to reach the apply step, which is exactly why step 2 exists.)
2. **Force** (the enforcers): install the project-scoped pieces into the repo:

   ```bash
   /path/to/pi-opsx-dev-reviewer/install.sh --here .
   ```

   This copies the project-local guard set into `<repo>/.pi/extensions/`, the `tools/`,
   and the `dev-reviewer` schema, scaffolds `AGENTS.md` + `learnings/` + `goals/`, and
   wires the recipe `justfile.opsx` via an `import` — **non-destructively** (`cp -n`;
   never clobbers your data; skips the schema if the repo already uses a different one).
   The global-only `worktree-canary` is deliberately excluded from local extension copies.
   Then the installer runs `just check-extensions` to prove the guards load clean.

   The `harness-selftest` canary prints a loud `HARNESS UNGUARDED` banner at startup if
   `force-delegate` failed to load, so a silent enforcer failure can never pass unnoticed.
   `developer-guard` blocks catastrophic bash (recursive-force `rm`, force-push, `sudo`,
   `dd`/`mkfs` to devices, curl-pipe-shell, fork bombs) for the write-capable subagents,
   which `force-delegate` deliberately leaves unguarded. `branch-guard` enforces PR flow —
   it blocks committing on `main`/`master`, pushing to them, and force-pushing to them, for
   every agent, so the developer subagent (which keeps full bash) can never land code on a
   protected branch without a reviewed pull request. Edit its `PROTECTED` set per project.
   `repeat-call-detector` blocks any agent that issues the same tool call with the same input
   eight times in a row, the signature of a loop that prints nothing new.
   Now the main agent can only run read-only bash and must delegate every mutation;
   the `solution-architect` subagent is path-gated to design artifacts. `/opsx:apply`
   must delegate.
3. Run `/opsx:apply <change>` and watch it fan out developer → reviewer per task.

## Run concurrent changes in worktrees

First run the global setup once on the machine. Besides the agents and prompts, this installs
the global fail-closed canary outside any checkout:

```bash
./install.sh
```

Create and enter a session worktree from the **primary checkout**:

```bash
just worktree add-foo
cd ../pi-opsx-dev-reviewer--add-foo
pi
```

`just worktree <name>` creates the sibling `../<repo>--<name>` on branch
`session/<name>`. It provisions only worktree-local, gitignored state: the local guard set
under `.pi/extensions/` and a `memory` symlink to the primary checkout. Tracked `openspec/`,
`tools/`, `schemas/`, and `config.yaml` come from the Git checkout and are not recopied.
Work on exactly one active OpenSpec change in that worktree and its branch.

Every checkout carries the tracked `.harness-marker`. The globally installed canary detects
that marker even when a linked worktree is bare or was not provisioned. At session startup,
a top-level `force-delegate` must prove that it loaded with a current-process PID handshake;
otherwise the canary prints `HARNESS UNGUARDED` and exits loudly before commands can run.
Valid delegated children are exempt and retain their full tools. The canary remains global-only:
if an older install left `.pi/extensions/worktree-canary` locally, `--here` and `--guards`
refuse to proceed. Inspect that path and remove it manually only after confirming it is the stale
local copy, then rerun the installer.

The `memory/` link is shared, but its writers use the narrowest safe concurrency model:

- `memory/trust.tsv` is a whole-file read-modify-write ledger, so updates are locked and
  committed with an atomic rename.
- `memory/goal-ledger.tsv` and `memory/tool-events.jsonl` remain plain, lock-free appends.
- Per-goal `goals/<name>.md` files belong to the individual worktree.

Do not parallelize changes that modify the same `openspec/specs/<capability>`; their promoted
deltas collide at merge. Archive each change from its owning worktree branch using the guarded
close-out flow, then land that branch through a pull request.

When finished, return to the primary checkout and remove only the named sibling:

```bash
just worktree-rm add-foo
```

The removal recipe validates the registered `session/<name>` worktree, removes that worktree's
local `.pi` and `memory` symlink, removes and prunes the worktree registration, and leaves the
primary `memory/` target and shared Git object store intact.

## Close an OpenSpec change

After the last task, delegate the docs artifact and run `/opsx-retro <change>`. Then close
with the guarded command:

```bash
just archive-change add-foo
```

The recipe runs the ledger gate, promotion guard, OpenSpec archival, and promoted-spec lint
normalisation in sequence. Do not run raw `openspec archive` as a close-out command.

The main agent has a narrow bookkeeping channel for exactly two recipes:
`just record-verdict` and `just archive-change`. It still cannot use `write`, `edit`, other
`just` recipes, redirection, output flags, environment assignments, or arbitrary shell
mutation. The developer subagent continues to author code, specs, and design artifacts.

Before `/opsx-loop`, run pi's `/session` in the persisted top-level session and copy its
absolute `File:` path. The loop protocol requires that absolute persisted session path,
quoted as its second argument; `<session.jsonl>` is shell redirection, not a placeholder.

```text
/opsx-loop add-foo "/Users/alice/.pi/agent/sessions/--work-repo--/session.jsonl"
```

The loop records each verdict before the developer ticks its task through the rendered
command:

```bash
just record-verdict "add-foo" "/Users/alice/.pi/agent/sessions/--work-repo--/session.jsonl"
```

That absolute-path rule belongs to the loop protocol. The `record-verdict` recorder itself
accepts any readable path, including a relative path, before validating the transcript.

If `archive-change` refuses `UNSAFE_PARTIAL_MODIFIED`, use the agent-driven intelligent
merge only for the capability named by the guard. Fully restate that merged `MODIFIED`
requirement, including its body and every scenario, then retry `just archive-change <change>`.
The retry guards every capability. See [the close-out guide](docs/close-out.md) for the full
operator procedure.

**Clobber-proof alternative to the extension:** use the bundled `dev-reviewer` OpenSpec
schema (`openspec/schemas/dev-reviewer/`), which bakes the delegation protocol into the
`apply` template and adds `review-report`, `docs`, and `architecture` artifacts. Copy it under
`<repo>/openspec/schemas/`, then select it (`--schema dev-reviewer` or in
`openspec/config.yaml`). `openspec update` won't overwrite a project schema (it *does*
regenerate — and would clobber — the generated `.pi/prompts/opsx-apply.md`, so never
hand-edit that file).

## Executed-evidence gates

Each of these checks something an agent could otherwise just assert. All are deterministic, run
without a model, and fail with the file and line that tripped them.

| Gate | What it fails on | Who runs it |
| --- | --- | --- |
| BLOCK-round cap | A task that has collected three `BLOCK` verdicts. `record-verdict` appends a `PARKED:` entry and exits 3, and `/opsx-loop` stops for you instead of re-dispatching. Tune with `OPSX_MAX_BLOCK_ROUNDS`. | The orchestrator, through `just record-verdict` |
| `just diff-gate` | A diff that adds a test skip or focus marker (`.skip(`, `.only(`, `#[ignore]`, and similar), and, with `--change <name>`, a ticked task that changed none of its declared source files. | The reviewer, on every task |
| `just claim-scan` | A version number or size added to a doc that no other file in the repo contains, or a file path in backticks that does not exist. | The tech-writer, before returning |
| `repeat-call-detector` | The eighth identical consecutive tool call from any agent. Tune with `OPSX_REPEAT_CALL_LIMIT`. | Every agent, as an extension |
| `just pi-compat` | Any "verified against pi X" claim that disagrees with [docs/pi-compatibility.md](docs/pi-compatibility.md). It also prints your installed pi next to that line, without failing on a difference. | You, when you bump pi |

`diff-gate` and `claim-scan` compare against the merge-base with `origin/main` by default;
pass `--base <ref>` for a stacked branch. Both are read-only, which is why the reviewer may run
them. The ideas come from [pi-rukas](https://github.com/trail-openers/pi-rukas) (Apache-2.0); the
decision record is [ADR 0006](docs/decisions/0006-port-pi-rukas-gates.md).

## Continual learning (the harness gets smarter each pass)

Every change ratchets into durable back-pressure so the next one is cheaper:

- **Scoped learnings** (`learnings/`) — `/opsx-retro` distils recurring review findings into
  glob-scoped rules with provenance and a `draft → active` promotion gate. At BRIEF,
  `just learnings-preview` runs the changed files through `tools/select-learnings.ts` and hands
  the developer only the learnings that match *those* paths — the scoped tier `AGENTS.md` can't
  be. `just check-learnings` (canary) and `just learnings-audit` (provenance) guard it.
- **Per-skill trust ledger** (`just trust`) — every completed task logs a pass/fail; autonomy
  graduates per skill: `auto` (≥20 runs, ≥95%), `watch` (<10 runs or <90%), `queue` between.
- **Standing goals** (`goals/`, `just goals`) — a finished change graduates into a `predicate:`
  re-verified daily; a regression flips it `VIOLATED` and fails loud. Nothing that passed once
  goes unwatched.
- **Weekly compost** (`/opsx-compost`) — reads the week's failures across changes, trust, and
  goals and proposes at most three new laws for your sign-off.
- **Session cost rollup** (`just session-cost <session.jsonl>`) — totals a pi session's cost per
  model (which `pi --export` does not), and flags subagent calls whose cost is TUI-only.
- **Tool-event assessment** (`just tool-events`) — the guards log every *blocked* action to
  `memory/tool-events.jsonl`; this mines that ledger (and, with `--session`, retry loops in a pi
  session) into candidate learnings for `/opsx-retro` — process friction the verdicts miss.
- **Refutation format** — every learning carries `conjectured → refuted_by → learned →
  criterion_now` (the Algorithm's hard-to-vary Changelog shape) so knowledge compounds instead
  of piling up.
- **Reproduce-first** — a bug-fix task's first probe must be a failing reproduction (red→green);
  the reviewer BLOCKs a fix with no repro.
- **Commitment-boundary advice** (`/opsx-advise`) — a cross-family second opinion on the
  *approach* (not the spec, not the diff) before the expensive build commits.
- **The meta-loop** — `/opsx-retro` writes a per-change reflection; `/opsx-compost` mines those
  reflections plus the trust / goals / tool-event signals and proposes **process/doctrine**
  changes — propose-only, human sign-off, grounded in evidence, never self-applied.

The exact command sequence by cadence (inner loop → ratchet → daily → weekly) is in
[`index.html`](index.html) under "The continual-learning lifecycle". Routing rule: global
invariants live in `AGENTS.md`, path-scoped rules in `learnings/`, verdicts in `review-log.md`.

## Verify

- Read-only reviewer proof:
  `pi -p --tools read,find,ls,grep "edit any file here"` → it refuses to write.
- End-to-end delegation:
  `pi -p "delegate to the reviewer agent: list md files here"` → returns the
  reviewer's `VERDICT: PASS …`.
- Force proof (in a repo with the extension): remove the delegate fallback so a blocked
  write has nowhere to go, then confirm the main agent cannot write:

  ```bash
  pi -p -a --exclude-tools subagent "use the write tool to create /tmp/x with PROOF"
  ```

  → the agent reports the write was blocked and `/tmp/x` is never created. (Without
  `--exclude-tools subagent` the main agent is still blocked, but it delegates and the
  developer subagent does the write — so the file appearing is delegation working, not the
  guard failing. Measure the block, not the side effect.)

## Recommended environment

Two optional settings sharpen the loop without changing its behaviour:

- **LSP back-pressure for the developer.** Give the developer's pi session an
  LSP/diagnostics extension (e.g. `pi-lens` or `@narumitw/pi-lsp`) so type errors and
  lint findings reach the agent as tool feedback. A defect the developer's own tools
  catch never has to reach the cross-family reviewer — the cheapest review is the one
  you don't pay a second model for.
- **Prompt-cache hygiene.** The agent files and prompt templates are byte-stable across
  iterations, so pi's prompt cache reads them at a fraction of the write cost. For long
  apply sessions set `PI_CACHE_RETENTION=long` (1-hour Anthropic / 24-hour OpenAI TTL)
  so the cache survives the gaps between delegations.

## Running on a Cursor subscription

When `openai-codex` credits run out, [`@schultzp2020/pi-cursor`](https://pi.dev/packages/@schultzp2020/pi-cursor)
routes every agent through a single Cursor subscription. It carries the OpenAI *and* Anthropic
lines, so it is also the cheapest way to get genuine cross-family review — the developer on
`gpt-5.6-sol`, the reviewer on `claude-opus-5`, one bill.

Install it alone. `pi-cursor-sdk` registers the same `cursor` provider name and wins the
routing, but it authenticates with a Cursor **SDK API key** and explicitly does not reuse
subscription OAuth — so every call fails `Invalid User API Key` no matter how recently you
logged in. If you have both, `pi remove npm:pi-cursor-sdk`.

### Switching model line-ups

`just models <profile>` writes project-local agent overrides into `.pi/agents/`, which the
subagent extension prefers over the global agents directory (precedence is user < project).
`.pi/` is gitignored, so a temporary line-up cannot be committed by accident, and the committed
pins in `agents/*.md` are never edited.

```bash
just models status        # effective pins + a cross-family check
just models cursor        # same models as the committed pins, billed to Cursor
just models cursor-xfam   # ... plus judges on the Anthropic line (recommended)
just models anthropic     # direct OAuth: 1M context, single-family
just models split         # cursor implementers, direct-Anthropic judges
just models off           # delete the overrides; committed pins apply again
```

**pi has two model layers, and they live in different places.** The subagent pins are read from
agent files; pi's *own* session model is `defaultProvider`/`defaultModel` in
`~/.pi/agent/settings.json`, which is what `/model` rewrites. Switching only the first leaves the
orchestrator silently on whatever `/model` last set — which reads as "the toggle did not work".
`just models` therefore sets both, and `status` reports both. Each profile carries a `_session`
pin; `off` restores `sessionDefault`. `settings.json` is backed up to `settings.json.orig` before
the first write.

Profiles live in `model-profiles.json`. Validate every id against `pi --list-models` before
adding one: the Cursor catalogue uses effort suffixes (`-low`/`-medium`/`-high`/`-xhigh`/`-max`)
and a separate `-thinking-` infix, so ids are not interchangeable with the direct-provider
spelling. `status` reports the *training family* rather than the provider, because Cursor is a
transport for several families at once — `cursor/gpt-5.6-sol-high` and
`cursor/claude-opus-5-thinking-high` are cross-family despite sharing a provider string.

### Patching the proxy for long agentic sessions (historical)

> **Superseded 2026-08-02.** The proxy-based `@schultzp2020/pi-cursor` was replaced by
> [`@rahularya01/pi-cursor`](https://www.npmjs.com/package/@rahularya01/pi-cursor), a **native**
> provider that streams Connect/protobuf over HTTP/2 from inside pi. No local proxy exists, so
> none of the five failure modes below can occur — they were all properties of the proxy layer.
> `tools/patch-cursor-heartbeat.ts` now exits with "package not installed", by design.
>
> Two things changed with the swap. The native provider ships a **different, smaller catalogue** —
> it tops out at `gpt-5.5-max` and `claude-4.6-opus`, so `gpt-5.6-sol/terra` and `claude-opus-5`
> are not available through Cursor any more; `model-profiles.json` was remapped accordingly. And
> both extensions register the provider name `cursor`, so they must never be installed together —
> that collision is what produced the original `Invalid User API Key`.
>
> The section is kept because the diagnoses are reusable, and because rolling back is a real option
> if the native provider disappoints.

The extension is tuned for interactive chat: short turns, few tool calls, no long silences.
A `/opsx-loop` run is the opposite, and stock settings kill it four different ways. All four
were diagnosed on 2026-07-31 and are documented here so they can be re-applied.

| Setting | Stock | Patched | Failure it causes |
| --- | --- | --- | --- |
| `HEARTBEAT_TIMEOUT_MS` (proxy) | `30s` | `10min` | Session pruned mid-turn, proxy self-terminates: `No active sessions, shutting down` |
| `HEARTBEAT_TIMEOUT_MS` (client) | `2s` | `10s` | Heartbeat POST times out under a busy event loop, compounding the above |
| `INACTIVITY_STREAMING_MS` | `15s` | `2min` | Stream closed after `15s` of silence → `[Error: session closed]` mid-generation |
| `INACTIVITY_THINKING_MS` | `30s` | `5min` | Same, during extended reasoning |
| `http://localhost:` (×7) | — | `http://127.0.0.1:` | `localhost` resolves to `::1` *and* `127.0.0.1`, so undici races both; a socket caught in that handoff throws `setTypeOfService EINVAL`, which is uncaught and exits pi outright |
| `MAX_BLOB_COUNT` | 128 | 2048 | Blobs LRU-evicted while still referenced → `GetBlob miss (store has 128 blobs)` → `Connect error internal` |
| `SESSION_TTL_MS` | `30min` | `6h` | Conversation state aged out mid-run |

Apply or re-apply after any `pi update`, reinstall, or version bump:

```bash
bun tools/patch-cursor-heartbeat.ts            # apply (idempotent)
bun tools/patch-cursor-heartbeat.ts --status   # report only, changes nothing
bun tools/patch-cursor-heartbeat.ts --revert   # restore the .orig backups
```

The script refuses to guess. Every edit declares how many occurrences it expects, and if the
count does not match — because upstream refactored the bundle — it writes nothing and exits
non-zero. A loud failure after an upstream change beats a silent mis-patch. Backups are written
as `<file>.orig` beside each patched file on first run.

Three things to know when re-applying:

- **The proxy loads these at spawn.** It runs `detached: false` as a child of pi, receiving its
  token on stdin and reporting its port back over stdout — which is why it cannot usefully be
  started by hand, and why "restart the proxy" means "start a pi session". Kill any running
  proxy (`pkill -f pi-cursor/dist/proxy`) and remove the stale `~/.pi/agent/cursor-proxy.json`
  so the next session spawns a patched one.
- **`index.js` is loaded inside pi itself**, so pi must be fully restarted to pick up the
  loopback change — a new session in the same process is not enough.
- **A conversation already damaged by blob eviction cannot be repaired**; the blobs are gone.
  Move `$TMPDIR/pi-cursor-conversations` aside and start a fresh session rather than resuming.

None of this is a substitute for an upstream fix. The blob cap and the timeouts are tuning, but
undici calling `socket.setTypeOfService()` without a `try`/`catch` (`client-h1.js:1245`) turning
a cosmetic socket option into a process-fatal exception is a genuine bug worth reporting, as is
a shutdown path that fires while a request is still streaming.

## Docs gate

Documentation is held to the same standard as code: a role writes it, a gate checks it.
The `tech-writer` agent drafts docs structured by Diátaxis and styled to pass
`just docs-lint` (markdownlint + Vale + lychee + cspell). The `architecture-writer`
agent owns the separate repo-scoped `docs/architecture/` arc42 tree and verifies it with
`just arch-lint`; Well-Architected claims are resolved through `just waf-grounding`.

Two enforcement layers, with an honest boundary between them:

- **Presence** — the `dev-reviewer` OpenSpec schema declares `review-report`, `docs`, and
  `architecture` artifacts that `requires: tasks`, so the apply prompt drives the agents to produce them.
  OpenSpec itself does NOT enforce their presence: tested on 1.4.1, both
  `openspec validate <change> --strict` and `openspec archive <change>` succeed on a
  change with tasks complete but no `review-log.md` and no docs delta. To make presence a
  real gate, run `just archive-change <change>`. It runs the ledger check before promotion
  and archival, and hard-fails (never skips) when the review ledger is missing or empty.
- **Quality** — `just docs-lint` runs whatever tools are installed and **skips any that
  aren't** (printing a per-tool notice), so on a fresh clone it can pass without checking
  anything. `just arch-lint` is the architecture-specific gate: it checks the arc42 section
  tree, stated costs, ADR links, Well-Architected IDs, and repo evidence. `just archive-check`
  requires a refreshed architecture tree when `<change>` touches architecturally significant
  paths and records a skip reason otherwise. Run `just docs-lint-setup` once to
  install the full docs set; treat a run that skipped tools as "not fully checked", not
  "passed".

## Architecture diagrams

Mermaid is the default and needs no setup: `just arch-lint` requires a Mermaid diagram in the
context and scope, building block view, and deployment view sections of `docs/architecture/`.

**Structurizr is an optional extra**, for teams that want C4 context, container, and component
views derived from one model rather than a diagram per file. It never replaces Mermaid and a
generated SVG can never satisfy a Mermaid requirement. Full guide:
[`docs/structurizr.md`](docs/structurizr.md).

```bash
./install.sh --here /path/to/repo --with-structurizr   # only activation path
just structurizr-render                                # -> build/architecture/structurizr/
just structurizr-clean                                 # remove output owned by this run
./install.sh --here /path/to/repo --remove-structurizr # keeps your model
```

An ordinary install carries no Structurizr inventory and performs no Docker or Bun probe.

- **Prerequisites**: a *native* Docker engine on `linux/amd64` or `linux/arm64`, and Bun **1.3.14**
  exactly. Emulation is refused — no QEMU, binfmt, or Rosetta-for-Linux.
- **Pinned renderer**:
  `structurizr/structurizr:2026.06.28-playwright@sha256:9bdc861e8c94f77f5f73bde70bdee410a65b82cbe8d341d3919a9ebd0cb17f8c`.
  The retired `structurizr/cli` and `structurizr/lite` distributions are rejected.
- **Your model, your file**: `docs/architecture/structurizr/workspace.dsl` is seeded only when
  absent and never replaced. One file, at most 5 MiB, no includes, extension, scripts, or plugins.
- **Output is ignored, never committed**: `build/architecture/structurizr/` holds the view SVGs,
  the exported `workspace.json`, and a `manifest.json` recording source hash, image, native
  platform, versions, and every file's size and SHA-256.
- **SVG bytes are not a stable API.** The renderer writes wall-clock metadata, so two runs of an
  unchanged model can differ. The gate never compares two renders; the manifest is the stable
  contract.
- **Accept or reject, never rewrite.** Every SVG must be passive and self-contained — no script,
  event handler, foreign content, or external reference — or nothing is published.
- **One failure, fixed precedence**: `CONFIG INVOCATION` → `IO LOCK_BUSY` → `IO UNSAFE_OUTPUT`,
  `IO PATH` → `CONFIG PIN`, `CONFIG MODEL_PATH`, `CONFIG SOURCE_DIRECTIVE`,
  `CONFIG WORKSPACE_EXTENDS` → `DEPENDENCY DOCKER`, `DEPENDENCY PLATFORM`, `DEPENDENCY IMAGE`,
  `DEPENDENCY BUN_VERSION` → `VALIDATION DSL`, `VALIDATION TIMEOUT` → `RENDER JSON`, `RENDER SVG`,
  `RENDER TIMEOUT` → `CONSISTENCY JSON`, `CONSISTENCY LINEAGE`, `CONSISTENCY VIEW_KEY`,
  `CONSISTENCY SVG_SAFETY` → `IO PUBLISH`, `IO CLEANUP`. No fallback exists.
- **CI**: a native `linux/amd64` `ubuntu-24.04` job with only `contents: read`, pinned actions, and
  a renderer started from an empty environment carrying six named non-secret variables. Verified
  output uploads for 14 days.
- **Pin updates are reviewed**, and require native fixture evidence on *both* targets.

## Caveats (verified vs. adjust-per-machine)

- **pi extension load-breakers (learned the hard way — see [`SHAKEDOWN.md`](SHAKEDOWN.md)):**
  pi 0.79.9 loads `.ts` extensions with a fragile tokenizer that fails the whole file with
  `Unterminated string constant` and then **silently disables it**. Three constructs
  trigger it: regex literals (use `new RegExp("...")` instead), raw backticks, and
  apostrophes (even inside comments and double-quoted strings). `bun build`, `jiti`, and
  unit tests all miss this — only loading through `pi` catches it. Run `just check-extensions`
  (a mechanical guard) before shipping any extension change. The defect does not reproduce on
  pi 0.83.0 (see [docs/pi-compatibility.md](docs/pi-compatibility.md)), but the guard stays
  because the kit declares no minimum pi version.
- **Extension package name**: neither extension imports a runtime package name, so loading
  is package-name-independent. If your editor type-checks, the local package may be
  `@earendil-works/pi-coding-agent` *or* `@mariozechner/pi-coding-agent`.
- **Models** are the one thing to adjust per machine (provider availability).
- **Subagent extension is third-party** (`@mjakl/pi-subagent`) — pin/inspect before
  trusting it in sensitive repos.
- **`--exclude-tools edit,write,bash`** on the pi CLI is a lighter, extension-free
  hard-force, but it also blocks the main agent from ticking `tasks.md` checkboxes;
  the extension route avoids that by letting the developer subagent do the ticking.
