The unknown-unknowns of developing inside this harness

The dangerous risks here aren't bugs — they're places where the harness feels more rigorous than it is, and the seat you operate from can't see the difference.

Grounded in the kit's own code and pi's docs (read this session). Each item is tagged pi / kit fact where it's verified from source, or assessment where it's reasoning. Last reviewed 2026-07-08.

This harness is good at making the developer disciplined and the review structured — but it quietly relocates the risk to three places it does not guard: the brief, the spec, and you. Everything below is a specific instance of that.

1Manufactured rigor

The harness projects a strong sensation of rigor. Because force-delegate makes your seat read-only, you fly on instruments you can't independently calibrate. "Green" means two models agreed and a checkbox was ticked — not this is correct. Trust the weakest link, not the ceremony.

manufactured rigorpi / kit factassessment

The reviewer runs nothing

The reviewer is read-only (read/find/ls/grep, no bash), so the "empirical gate" — a BLOCK must name a runnable probe — is actually executed by the developer, the party motivated to pass. The reviewer names the probe; the developer runs it and self-reports. That's a fox-guarding-henhouse structure at the centre of the verification story.

manufactured rigorpi / kit factassessment

The reviewer currently shares the developer's blind spots

Everything is pinned to openai-codex right now. A PASS from gpt-5.4 on gpt-5.5's work is correlated blindness, not independent confirmation — the reviewer misses the class of bugs its own family makes. The sharp version: research documented ten same-corpus reviewers unanimously endorsing a vulnerability that didn't exist.

manufactured rigorpi / kit factassessment

The developer ticks its own box; the ledger is prompt-enforced

The only "done" signal is two subagents agreeing, and the developer marks its own task [x]. The compounding-findings story depends on the developer appending to review-log.md and you running /opsx-retro. archive-check only confirms a verdict exists — not that every finding was recorded or that the retro ran. The loop can silently fail to compound while still looking green.

2Silent failures in pi

These bite hardest because there's no error — the safety simply isn't there.

silent failurepi fact

The enforcers load only after project trust

pi loads .pi/extensions/ only after the project is trusted. In an untrusted project, a fresh clone, or a headless/CI run that didn't pre-approve trust, force-delegate and architect-scope don't load — and the main agent is silently not read-only. It will self-edit while you believe delegation is enforced. Run the README's "Force proof" (ask the main agent to write a file; confirm it's blocked) at the start of any session that matters.

silent failurepi factassessment

architect-scope fails open

It detects the architect from the tail of PI_SUBAGENT_STACK. If a future @mjakl/pi-subagent changes how that variable is populated, the check returns "unknown agent", the extension no-ops, and the architect silently regains full write access to your codebase. The degradation is invisible until the architect writes code it shouldn't.

silent failurekit fact

The developer is unsandboxed by design

The developer keeps full write + bash so it can do the work, and the kit ships no damage-control on it. force-delegate restricts your seat, not the worker. A hallucinated rm -rf or a bad migration from the developer executes. pi is YOLO-by-default; nothing here sandboxes the one agent that can actually destroy things.

silent failureobserved this session

Subagents die on transient provider errors

We hit this repeatedly today — a code subagent died twice mid-task on connection errors. A dead subagent can look like a partial or stalled task; if the orchestrator doesn't notice and retry, work gets marked as progressed that never actually happened.

3What you'll feel operationally

operationalresearch

Latency and cost multiply invisibly

Every task is at least two full pi process spawns (developer + reviewer), each a cold start replaying full context — multi-agent runs use roughly 15× the tokens of a single chat. A 20-task change with a few BLOCK loops is 50+ cold spawns. On a ChatGPT subscription it's within plan, but it will feel slow long before you'd notice a bill.

operationalassessment

You're out of the loop by design — the discipline trap

Your instinct to "just fix this one line myself" is blocked by force-delegate. The moment you disable the extension for a quick fix is the moment you lose the guarantee — and nothing in the harness can enforce discipline on you. That's the most common way setups like this quietly stop being real.

operationalpi factassessment

Briefing is the hidden bottleneck

Each subagent sees only its Task string and cannot ask a clarifying question (fresh offline process). An incomplete brief produces a confident wrong build, not an error. The main agent — the one component with no quality gate on its own output — sets the ceiling on every delegation.

4Where your leverage actually moved

leverage shiftassessment

The spec is now the contract, faithfully amplified

The point of a disciplined developer is fidelity to the spec — which means spec errors propagate with full confidence across every task. A wrong spec yields perfectly-built wrong software. Your attention needs to move upstream to the proposal and architect settlement, and that's currently the least-gated stage in the pipeline. That's the real trade: fewer implementation bugs, higher stakes on getting the spec right.

leverage shiftresearch

openspec update clobbers generated prompts

openspec update regenerates .pi/prompts/opsx-apply.md and would overwrite hand-edits. Customise the wrong file and a routine update silently reverts your delegation wiring — use the bundled dev-reviewer schema instead of hand-editing generated prompts.

5The honest meta

metafact

This harness has never run a live end-to-end delegation

It was hand-built in a single session. The extensions pass unit tests, the schema validates, the docs are clean — but no real /opsx:apply has ever driven the developer → reviewer → tech-writer → archive-check loop. The first few real changes are shakedown runs, not production; expect integration surprises the tests structurally could not catch.

6Turning these into managed risks

Unknown-unknowns are most useful paired with what converts them to managed. The short list:

  1. Confirm the enforcers engaged before trusting a session's read-only guarantee — run the "Force proof".
  2. Put the reviewer on a genuinely different family for anything you care about (anthropic/ is reachable on this machine); all-OpenAI is fine only for smoke-testing the mechanism.
  3. Add damage-control on the developer before any unattended run — it's the one agent that can destroy state.
  4. Spend your review attention on the spec and architect output, where errors are cheapest to kill and most expensive to miss.
  5. Don't trust a PASS without spot-checking that the reviewer's named probe was actually run and actually passed — that check is the one that collapses if you skip it.
