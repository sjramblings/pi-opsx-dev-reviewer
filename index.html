Protections, features, and how to use them

A portable kit that turns pi into a delegating, self-guarding software factory: a design → implement → review → document pipeline where the enforcement is structural, the review evidence is produced by a neutral party, and every guard fails closed and announces itself.

The pipeline

Five specialist subagents, each a separate pi process with its own model and tool allowlist. The main agent orchestrates and is structurally prevented from doing the work itself.

solution-architect→ spec-reviewer→ developer→ reviewer→ tech-writer→ archive

The architect settles the design and records ADRs; a cross-family spec-reviewer red-teams the spec before any code exists; the developer implements one task at a time against a frozen probe; a different-family reviewer grades the diff; the tech-writer documents what shipped; and a set of mechanical gates verify presence, evidence integrity, and load-safety before the change is archived.

The protection model

Eleven layers. Each is a structural control, not a prompt asking nicely.

delegation

Read-only main agent (force-delegate)

The main agent's write and edit are hard-blocked, and bash is deny-by-default with a read-only allowlist (openspec/git read verbs, ls cat rg grep find head tail wc echo jq). It blocks command substitution, redirection, command chaining to non-allowed commands, inline env-injection (GIT_PAGER=…), and find -exec. The only way to change code is to delegate to the developer subagent — so “please delegate” becomes “must delegate.”

fail closed

Architect confined to design artifacts (architect-scope)

The solution-architect can only write design artifacts (proposal.md, design.md, specs/**, docs/decisions/**). It fails closed: an unidentified or unparseable agent is restricted, not waved through — so a future change to how pi reports agent identity can never silently hand out unrestricted write.

fail closed

Startup self-test canary (harness-selftest)

The single scariest failure is a guard that silently doesn't load. This canary runs at session_start; if force-delegate did not load, it prints a loud HARNESS UNGUARDED banner and tells the agent to halt. A silent enforcer failure can no longer pass unnoticed.

fail closed

Damage-control on the workers (developer-guard)

The developer subagent keeps full tools by design, so it needs its own guard. This blocks catastrophic bash for every agent: recursive-force rm, git push --force, sudo, dd/mkfs to devices, redirect-to-device, recursive chmod on /, curl-pipe-to-shell, and fork bombs.

workflow

PR flow enforced (branch-guard)

The developer subagent keeps full bash, so it could git push origin main and land code with no review — exactly the bypass this closes. branch-guard blocks committing on main/master, pushing to them, and force-pushing to them, for every agent. The only way onto a protected branch becomes a reviewed pull request. Protected branches are configurable per project.

review integrity

Cross-family review

The reviewer runs on a different model family than the developer, so it does not share the developer's blind spots. On high-risk tasks a two-family quorum (OpenAI + Anthropic) must both pass.

review integrity

De-biased reviewer input + empirical gate

The developer's narrative is handed to the reviewer as AUTHOR CLAIMS (untrusted) — claims to test, not context to trust — and the reviewer audits beyond the areas the author points to. A BLOCK must rest on something runnable: a CONFIRMED defect, or a PLAUSIBLE one whose named probe fails. A hunch with no probe cannot block.

evidence

Neutral executor + attestation (the oracle)

No interested party produces its own evidence. just run-probe executes the frozen acceptance probe and writes a sha256-attested transcript into the ledger; just archive-check re-hashes it, so a hand-edited (tampered) result fails the archive. Probes are committed before implementation, so a passing test cannot be tuned to the code.

evidence

Compounding review ledger

Every verdict is appended to review-log.md instead of evaporating in a transcript. At archive time /opsx-retro distills recurring findings into durable rules (config, AGENTS.md, or lint), so each change makes the next one cheaper.

evidence

Scoped learning loop (learnings/)

The ledger compounds within a change; this compounds across them. /opsx-retro distills recurring findings into scoped learnings/ entries (typed, versioned frontmatter, a glob scope, immutable provenance, and a draft→active promotion gate). At BRIEF, just learnings-preview runs the changed files through tools/select-learnings.ts and hands the developer only the past learnings whose scope matches these paths — the scoped tier AGENTS.md cannot be. One fact, one home: global invariants in AGENTS.md, path-scoped rules in learnings/, verdicts in review-log.md.

autonomy

Per-skill trust ledger (just trust)

Autonomy is earned per skill, not per loop. Every completed task logs a pass/fail to memory/trust.tsv; the tally sets a tier — auto (≥20 runs and ≥95%), watch (<10 runs or <90%), queue between. A fail that drops an established skill below 90% prints a loud ALERT. It is the measured version of risk-tiering, backed by the reviewer verdicts already in the ledger. just trust renders the table; just trust-log <skill> <pass|fail> records a result.

invariant

Standing goals, re-verified forever (just goals)

A goal you only verify once is an assumption with a timestamp. A finished change graduates into goals/<name>.md whose predicate: is a shell command that must keep exiting 0. just goals (run daily) re-checks every predicate, flips satisfied↔VIOLATED in the file, appends to memory/goal-ledger.tsv, and exits non-zero on any regression — so a silent regression on something you were sure was done becomes loud. Detection here; the fix goes through the normal pipeline.

upstream

Spec red-team + brief gate

Because the developer faithfully amplifies the spec, a wrong spec becomes wrong software at scale. A cross-family spec-reviewer attacks the proposal/design for ambiguity, missing edge cases, and untestable requirements before any code. just brief-check bounces an underspecified delegation brief before the costly developer is even spawned.

supply chain

pi load-breaker guard (check-extensions)

pi's extension loader silently disables a file with a regex literal, a raw backtick, or an apostrophe. just check-extensions is a mechanical gate that rejects all three, so the class of bug that once left every guard dead-on-arrival can never regress. See SHAKEDOWN.md for the story.

OpenSpec schema & prompts

The dev-reviewer schema bakes the whole contract into the OpenSpec workflow so it survives openspec update (unlike a hand-edited prompt).

  • Artifacts: proposal → specs → design → tasks → review-report (the ledger) → docs (the doc delta). The apply template mandates developer→reviewer delegation.
  • Presence honesty: OpenSpec 1.4.1 does not hard-gate archive on a missing artifact — that is what just archive-check exists to enforce.
  • Prompt templates (~/.pi/agent/prompts/): /opsx-loop <change> drives the delegation loop, /opsx-review <change> runs one adversarial review, /opsx-retro <change> ratchets findings into rules before archive, /opsx-advise <change> gives a cross-family second opinion on the approach at commitment boundaries, and /opsx-compost mines a week of failures, reflections, and tool-events into at most three proposed changes.
  • Algorithm grafts: learnings carry a conjectured→refuted_by→learned→criterion_now refutation core; bug-fix tasks are reproduce-first (a failing repro is the first probe, red→green, or the reviewer BLOCKs); and the meta-loop (/opsx-retro reflection → /opsx-compost) proposes process/doctrine changes — propose-only, human sign-off, grounded in the empirical signals, never self-applied.
  • Scoped learning store (learnings/): /opsx-retro routes path-scoped findings here (not AGENTS.md), and /opsx-loop injects the matching ones at BRIEF via just learnings-preview — one fact, one writable home.
  • Trust ledger + standing goals: autonomy graduates per skill in memory/trust.tsv (just trust), and every finished change becomes a re-verified invariant in goals/ (just goals, daily) — nothing that passed once goes unwatched.

The continual-learning lifecycle

The guards and stores only compound if you run the loop. This is the exact command sequence by cadence — each pass leaves the harness knowing a little more.

Per change — the inner loop

  1. /opsx-loop <change> — drive each task through developer → reviewer. At BRIEF it auto-runs just learnings-preview, handing the developer the scoped learnings for the files it touches; every verdict is appended to review-log.md.
  2. just next <change> — at any point, where the change is and the one command to run next.
  3. just trust-log <skill> <pass|fail> — record each outcome so autonomy graduates per skill (just trust shows the tiers).

Closing a change — the ratchet

  1. /opsx-retro <change> — distil recurring findings into laws: global → AGENTS.md, path-scoped → learnings/ (draft), mechanical → a lint rule. Promote reviewed drafts to active.
  2. just learnings-audit + just check-learnings — confirm provenance, and that the retrieval path is live.
  3. just archive-check <change> → openspec archive <change> — graduate the change, then drop a goals/<name>.md predicate for what must stay true.

Daily — the sentinel

  1. just goals — re-verify every standing goal; a regression flips it to VIOLATED and fails loud. Wire it to cron / the verify-goals sentinel.

Weekly — the compost

  1. /opsx-compost — read the week's failures across changes, trust, and goals; propose at most three new laws for your sign-off.

Each pass leaves the harness knowing a little more — scoped learnings for next time, a higher trust tier, one more invariant guarded. Nothing that passed once goes unwatched.

How to use

1. Install (global, per machine)

./install.sh

Installs @mjakl/pi-subagent, copies the five agent files and the three prompt templates into ~/.pi/agent/, and prints a model sanity check. Adjust any model: line to what pi --list-models shows on your machine.

2. Use it ad hoc (no OpenSpec)

pi -p "Implement <X> with the developer agent, then have the
        reviewer agent check the diff and give me its verdict."

3. Force /opsx:apply through the subagents (per project)

  1. Copy the four extensions into the repo so pi loads them: 
    mkdir -p <repo>/.pi/extensions
cp -r extensions/force-delegate   <repo>/.pi/extensions/
cp -r extensions/architect-scope  <repo>/.pi/extensions/
cp -r extensions/harness-selftest <repo>/.pi/extensions/
cp -r extensions/developer-guard  <repo>/.pi/extensions/
  2. Select the schema (clobber-proof): copy openspec/schemas/dev-reviewer/ into the repo and set schema: dev-reviewer in openspec/config.yaml.
  3. Run /opsx:apply <change>. The main agent is now read-only, so it must delegate developer → reviewer per task.

4. The review lifecycle for one task

  1. Brief the developer — run just brief-check so the brief is self-contained.
  2. Gate deterministically — just verify-gate and just run-probe attest the frozen probe.
  3. Review — the reviewer receives the raw diff + attested evidence, with the developer's narrative quarantined as untrusted.
  4. Ledger — the verdict is appended to review-log.md; only a PASS (no P0/P1) completes the task.
  5. Retro — /opsx-retro ratchets recurring findings, then just archive-check guards the archive.

5. Verify the guard is actually on

The most important habit: confirm delegation is enforced by removing the fallback and checking the main agent cannot write. Measure the block, not the side effect.

pi -p -a --exclude-tools subagent \
  "use the write tool to create /tmp/x with PROOF"

The agent should report the write was blocked and /tmp/x should not exist. (Without --exclude-tools subagent the main agent is still blocked, but it delegates and the developer subagent does the write — so the file appearing is delegation working, not the guard failing.)

Writing pi extensions: hard constraints

pi 0.79.9 silently disables an extension whose source contains a regex literal, a raw backtick, or an apostrophe (even inside a comment or a double-quoted string) — it fails with Unterminated string constant and continues without it. bun build, jiti, and unit tests all miss this. Rules for any extension you add: use new RegExp("…") not /…/; no backticks; no apostrophes; keep every quote character balanced. Run just check-extensions before shipping — and verify the extension by loading it through pi, never by an offline check alone.
